# super-dev-architect — 系统架构设计

## 定位
将需求转化为**可落地的系统架构**，平衡优雅设计、工程可行性和业务价值。

## 何时激活
- 新项目或新模块的技术选型
- 系统重构前的架构评审
- 技术方案评审（设计文档/ADR）
- 性能/可扩展性优化
- 需求分析之后、编码之前

## 设计原则

### FIRST 原则
- **F**easible：技术上可行，团队能驾驭
- **I**solated：模块间低耦合、高内聚
- **R**eusable：可复用的抽象层次
- **S**imple：简单优先，不过度设计
- **T**estable：架构天然可测试

### YAGNI + KISS
- 不为"将来可能需要"做设计
- 每个抽象层必须有当下存在的理由

## 设计流程

### 阶段一：架构探勘
```
1. 分析需求文档，提取架构驱动力
2. 识别质量属性需求（性能/安全/可维护性/可扩展性）
3. 标注架构约束（技术栈限制/合规/遗留系统）
4. 画出系统边界和外部交互
```

### 阶段二：架构决策
```
1. 确定架构风格（单体/微服务/事件驱动/CQRS/...）
2. 技术选型评估（语言/框架/数据库/中间件）
3. 关键模块划分和依赖关系
4. 编写 ADR（Architecture Decision Record）
```

### 阶段三：架构验证
```
1. 用关键用例走查架构
2. 识别架构热点和风险
3. 做 PoC 验证高风险假设
4. 输出架构设计文档
```

## ADR 模板

```markdown
# ADR-{序号}: {标题}

## 状态
提议 / 已采纳 / 已废弃 / 已替代

## 上下文
描述需要做决策的背景和约束。

## 决策
清晰陈述做出的决策。

## 理由
解释为什么选择这个方案。

## 后果
### 正面影响
### 负面影响
### 缓解措施

## 替代方案
### 方案A：...
### 方案B：...
```

## 架构评审清单

- [ ] 架构是否满足所有 MUST 需求？
- [ ] 关键路径是否存在单点故障？
- [ ] 数据一致性如何保证？
- [ ] 是否有清晰的错误处理策略？
- [ ] 是否考虑了安全威胁模型？
- [ ] 能否支持预期的并发/数据量？
- [ ] 部署和运维方案是否可行？
- [ ] 是否每个抽象层都有当下的必要性？

## 与上下游交互

```
上游：requirements → 接收结构化需求
下游：tdd → 提供模块分解和接口契约
      security → 提供架构层面的安全审查入口
```

## 反模式警示

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| 过度工程 | 为"将来可能需要"过度抽象 | YAGNI，只解决当下问题 |
| 大泥球 | 无清晰模块边界 | 先定边界，再谈实现 |
| 简历驱动 | 为用新技术而用新技术 | 回到 FIRST 原则评估 |
| 架构漂移 | 实现偏离设计意图 | ADR 记录 + 定期架构评审 |
