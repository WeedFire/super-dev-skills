# super-dev-evolution — 技能自我进化

## 定位
使 super-dev 套件具备**自我感知、自我优化、自我进化**的能力。周期性审视自身结构，发现改进机会，自动提炼新 Skill。

## 何时激活
- 套件定期自检（建议每周）
- 里程碑或版本发布后
- 发现新的高频使用模式
- 某个子 Skill 变得臃肿（>300 行）
- 用户反馈某个环节有问题
- 新工具/新实践出现

## 进化循环

```
┌─────────────────────────────────────────┐
│            技能进化循环                   │
│                                         │
│  1. OBSERVE   收集使用数据和反馈          │
│       ↓                                 │
│  2. ANALYZE   识别模式和瓶颈              │
│       ↓                                 │
│  3. PROPOSE   提出进化方案               │
│       ↓                                 │
│  4. VALIDATE  验证改进效果               │
│       ↓                                 │
│  5. EVOLVE    实施进化 → 记录变更日志     │
└─────────────────────────────────────────┘
```

## Step 1: OBSERVE — 数据采集

### 采集维度
```yaml
usage_metrics:
  - 每个子 Skill 的激活频率
  - 平均上下文消耗（指令行数）
  - 任务完成时间
  - 用户满意度信号（中断/修正/点赞）
  
quality_metrics:
  - 各阶段缺陷逃逸率
  - 安全漏洞检出率
  - UX 返工率
  - 架构决策回溯率（ADR 被废弃比例）
  
growth_metrics:
  - 新增记忆条目数
  - 模式库增长
  - 领域记忆覆盖度
```

### 数据来源
```
- 记忆系统统计（memory/index.md）
- 代码变更记录（git log）
- 用户反馈汇总
- 套件自身变更历史（.codebuddy/skills/ 的 git log）
```

## Step 2: ANALYZE — 模式识别

### 臃肿检测
```
信号：
  □ 某 Skill 文件 > 300 行
  □ 某 Skill 内包含多个不相关主题
  □ 激活该 Skill 时上下文经常超限

响应：提出拆分方案
```

### 低利用率检测
```
信号：
  □ 某 Skill 连续 2 周未被激活
  □ 某 Skill 的功能被其他 Skill 覆盖
  
响应：评估合并或废弃
```

### 高频协作检测
```
信号：
  □ 某两个 Skill 经常被连续激活
  □ 每次协作都要重复传递相同上下文
  
响应：评估合并或创建桥接 Skill
```

### 新能力发现
```
信号：
  □ 同一类任务被反复执行但不属于现有 Skill
  □ 记忆中出现高频新标签
  □ 用户要求做"非标准"操作
  
响应：提议创建新子 Skill
```

## Step 3: PROPOSE — 进化提案

### 提案模板
```markdown
# 进化提案 EP-{序号}：{标题}

## 触发信号
描述观察到的数据和模式。

## 当前状态
描述现有架构/配置的问题。

## 提议变更
- 类型：拆分 / 合并 / 新增 / 废弃 / 优化
- 涉及 Skill：[列表]
- 变更内容：[具体描述]

## 预期收益
- 上下文节省：约 X%
- 响应速度提升：约 Y%
- 用户体验改善：[具体描述]

## 潜在风险
- [风险点]：[缓解措施]

## 验证计划
如何验证改进有效？

## 回滚方案
如果改进无效，如何回退？
```

## Step 4: VALIDATE — 验证改进

### A/B 对比
```
改进前：
  - 记录基线指标（激活频率、上下文长度、任务完成时间）
  
改进后（试用 3-5 个任务）：
  - 收集新指标
  - 对比基线
  
判定标准：
  - 上下文节省 ≥ 10% → 采纳
  - 用户主观评价提升 → 采纳
  - 指标恶化 → 回滚
```

## Step 5: EVOLVE — 实施进化

### 变更日志
```markdown
# 套件进化日志

## v2.1.0 (YYYY-MM-DD)
### 拆分
- super-dev-tdd → tdd-core + tdd-web + tdd-api
  原因：原 TDD Skill 达 350 行，激活时加载过多无关内容

### 新增
- super-dev-api-design.md
  原因：API 设计相关任务月均 12 次，独立激活需求明显

### 优化
- 所有 Skill 增加"最小激活上下文"标记
  原因：按需加载关键段落，减少 30% 上下文消耗

### 废弃
- super-dev-docker.md（合并到 architect 部署架构章节）
  原因：激活频率低，内容与其他 Skill 重叠
```

## 进化触发规则

### 自动触发（由 Orchestrator 调度）
```
每周自检：
  □ 运行臃肿检测
  □ 检查低利用率 Skill
  □ 总结本周新发现模式
  → 生成观察报告
  → 如有显著信号，生成进化提案
```

### 手动触发
```
用户：进化 super-dev 套件
用户：检查套件是否需要优化
用户：最近 XX Skill 用起来不太顺手
```

## 与 Memory 系统交互

```
读取：evolution 读取 memory 中的使用统计
写入：evolution 将进化决策记录到项目记忆
关联：每次进化可能产生新的领域记忆
```

## 反模式警示

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| 过度拆分 | 拆得太细，激活路径复杂 | 拆分后 Skill 应 ≥ 50 行有效指令 |
| 为改而改 | 没有数据支撑的优化 | 所有提案必须有数据依据 |
| 进化停滞 | 发现信号但不处理 | 设置每周自检提醒 |
| 破坏性进化 | 改动后旧经验失效 | 保持向后兼容，渐进式迁移 |
| 忽略用户 | 只看数据不看反馈 | 用户主观体验权重 > 纯数据 |
