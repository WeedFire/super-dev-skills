# super-dev-requirements — 需求深访与结构化

## 定位
将模糊的用户意图转化为**精确、可验证、无歧义**的结构化需求文档，建立团队共享语言。

## 何时激活
- 用户提出新功能需求
- 现有功能需要变更
- Product Backlog 梳理
- 需求评审前准备
- 用户说"我想要……"、"能不能做一个……"

## 核心方法论：深度需求访谈

### 访谈框架（5W2H-D）

```
What    — 要做什么？（功能边界）
Why     — 为什么要做？（业务价值）
Who     — 谁用？（用户画像）
When    — 什么时候用？（使用场景/时机）
Where   — 在什么环境下用？（设备/网络/上下文）
How     — 怎么用？（交互流程）
How Much— 成本/收益比
Detail  — 细节挖掘（边界情况、异常处理）
```

### 访谈过程

**第一轮：发散探查**
```
1. 用开放式问题了解全貌
2. 不做判断，只记录
3. 发现隐含假设并标记
```

**第二轮：收敛确认**
```
1. 逐一确认不明确的点
2. 用"如果……会怎样"探测边界
3. 输出初步用户故事
```

**第三轮：验收对齐**
```
1. 与用户逐条确认验收标准
2. 确保每个故事都有 Given-When-Then
3. 标记优先级（Must/Should/Could/Won't）
```

## 产出规范

### 用户故事模板
```
作为 <角色>，
我想要 <功能>，
以便 <价值>。

验收标准：
- Given <前置条件>
- When <操作>
- Then <预期结果>

优先级：Must / Should / Could / Won't
复杂度估算：XS / S / M / L / XL
```

### 需求文档结构
```markdown
# [功能名称] 需求规格

## 1. 业务背景
## 2. 用户画像
## 3. 核心流程
## 4. 用户故事列表
## 5. 验收标准矩阵
## 6. 非功能需求（性能/安全/可访问性）
## 7. 边界与约束
## 8. 依赖与风险
```

## 共享语言建立

在需求访谈过程中，同步建立领域术语表：
```
术语        | 定义                  | 别名/别称 | 示例
------------|-----------------------|-----------|------
订单(Order) | 用户发起的购买请求     | 交易       | "用户下单"
会话(Sess)  | 用户的一次访问周期     | 登录态    | "会话过期"
```

## 需求质量检查清单

- [ ] 每个用户故事是否有明确的验收标准？
- [ ] 是否覆盖了正常流程、异常流程、边界情况？
- [ ] 是否存在隐含假设未被显式确认？
- [ ] 术语是否在团队内达成共识？
- [ ] 是否明确了"不做什么"（Out of Scope）？
- [ ] 非功能需求是否已明确（性能/安全/UX）？
- [ ] 依赖项是否已识别并评估风险？

## 与 Orchestrator 交互

```
输入：用户原始意图描述
输出：结构化需求文档 + 共享语言术语表
触发下一阶段：architect（架构设计）或 tdd（直接开发）
```

## 反模式警示

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| 过早设计 | 需求阶段就讨论实现细节 | 先问 What，再问 How |
| 主观臆断 | 替用户做决定 | 必须确认，不做假设 |
| 范围蔓延 | 越问越多，失去焦点 | 坚持 MVP 思维，标注后续迭代 |
| 验收模糊 | "基本能用就行" | 必须可测量、可自动化验证 |
